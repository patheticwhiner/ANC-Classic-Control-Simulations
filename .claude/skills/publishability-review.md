# 学术发表可行性内部审稿

对项目中的 demo 代码与配套文档，以"审稿人视角 · 内部评审"的框架进行系统性发表可行性评估，输出一份结构完整的审稿意见。

## 重要：审稿之前必须先了解被审稿内容

在写审稿意见之前，必须完整阅读目标目录下的所有关键文件。阅读范围至少包括：
- 所有 `.m` 仿真/算法脚本
- 所有 `.md` 文档
- `README.md`（如有）
- `functions/` 或 `utils/` 下的核心函数

阅读完成后，在审稿意见末尾标注阅读范围（参考模板中的 `<p align="right">` 脚注）。

## 审稿意见结构（8 个模块，严格按顺序）

### 模块 0：标题区

```markdown
# <font color="#1a1a2e">审稿意见</font>

## <font color="#1a1a2e">[demo编号/名称] —— 学术发表可行性评估</font>

> <font color="#555555"><b>审稿人视角 · 内部评审</b>　|　[一句话技术定位描述]</font>

---
```

### 模块 1：§1 总评

**决策横幅**（用橙色大横幅，三种决策措辞之一）：
- `Major Revision（大修）` — 有可发表的原子但需大量补充工作
- `Not suitable as a research paper in current form` — 当前形式不适合作为研究论文
- `Minor Revision（小修）` — 接近可投稿，需补充局部内容

**正文**：一段话总结本工作做了什么。

**双列表格**：✅ 主要贡献 / ❌ 主要不足，各 3-4 条。每条用 `<u>` 标注关键词，不足用带圈数字❶❷❸编号。

```markdown
| <font color="#27ae60"><b>✅ 主要贡献</b></font> | <font color="#c0392b"><b>❌ 主要不足</b></font> |
|:---|:---|
| ... | ❶ ...<br>❷ ...<br>❸ ... |
```

### 模块 2：§2 逐项评估

#### §2.1 新颖性 (Novelty)

**表格**：技术要素 | 来源 | 审稿意见，每行标注颜色：
- 非原创 → `<font color="#c0392b"><b>✗ 非原创</b></font>`
- 增量贡献 → `<font color="#e67e22"><b>△ 增量贡献</b></font>`
- 主要新颖性 → `<font color="#27ae60"><b>★ 主要新颖性</b></font>`
- 教学/指导价值 → `<font color="#2980b9"><b>◈ 有指导价值</b></font>`

来源列使用颜色区分：作者独立完成用蓝色 `#2980b9`，已有文献用灰色 `#7f8c8d`。

**审稿意见段落**（红色引导）：明确指出核心新颖性所在，以及当前未聚焦的贡献点。

#### §2.2 理论完备性 (Theoretical Rigor)

用引用块逐条列出问题，按严重程度分级：

- `<font color="#c0392b"><b>❶ 严重</b></font>` — 理论缺口，必须补
- `<font color="#e67e22"><b>❷ 中等</b></font>` — 推导不充分
- `<font color="#7f8c8d"><b>❸/❹ 轻微</b></font>` — 表述问题

每条格式：问题名称用 `<b><u>` 加粗下划线，正文说明问题，蓝色箭头 `→` 给出改进方向。

也应有 ✅ 已有且质量优秀的内容（绿色标注）。

#### §2.3 实验验证 (Experimental Validation)

- `<font color="#27ae60"><b>✅ 已有内容</b></font>` — 列表
- `<font color="#c0392b"><b>❌ 缺失内容</b></font>` — 列表，按重要性排序：

分级：
- `<font color="#c0392b"><b>❶ 必需</b></font>` / `<font color="#c0392b"><b>❶ 关键阻塞</b></font>`
- `<font color="#e67e22"><b>❷ 强烈建议</b></font>`
- `<font color="#2980b9"><b>❸/❹ 建议</b></font>`
- `<font color="#7f8c8d"><b>❺ 可选</b></font>`

#### §2.4 表述与结构 (Presentation)

双列表格：✅ 优势 | ⚠ 从学术论文视角看的问题

### 模块 3：§3 按期刊层级的可行性评估

**表格**：期刊 / 会议 | 可行性 | 所需追加工作 | 预期篇幅

可行性颜色：
- `<font color="#c0392b"><b>✗ 不可行</b></font>`
- `<font color="#e67e22"><b>△ 困难 / 有可能</b></font>`
- `<font color="#2980b9"><b>◈ 最可行的期刊目标</b></font>`
- `<font color="#27ae60"><b>● 可直接投稿 / 非常适合</b></font>`

期刊层级覆盖（按声望降序）：
1. IEEE TAC / Automatica
2. IEEE/ACM TASLP
3. MSSP / JVC / Control Engineering Practice
4. Applied Acoustics / IEEE Access
5. IEEE SPL / IEEE CSM / IFAC ACE / SoftwareX
6. InterNoise / ICSV / GitHub+arXiv

**推荐策略段落**（蓝色引导）：给出最可行的投稿路径和切分建议。

### 模块 4：§4 修改建议（按优先级排列）

三个优先级，每个包含若干编号条目（①②③…）：

- **优先级 1** · `<font color="#c0392b"><b>必须完成</b></font>` <small>（否则不建议投稿任何期刊）</small>
- **优先级 2** · `<font color="#e67e22"><b>强烈建议</b></font>` <small>（目标期刊级别需要）</small>
- **优先级 3** · `<font color="#7f8c8d"><b>锦上添花</b></font>` <small>（更高级别期刊需要）</small>

每条建议用引用块，加粗下划线标题 + 正文说明。

### 模块 5：§5 最终建议

**核心叙事结构**（必须包含）：

1. **"不是……而是……"句式**：明确指出本工作最有价值的<font color="#c0392b"><b>不是</b></font> X（已有方法/框架），也<font color="#c0392b"><b>不是</b></font> Y（其他非原创部分），<font color="#27ae60"><b>而是</b></font> Z（真正的贡献）。

2. **引用块金句**（灰色斜体）：用一句简洁有力的话概括核心贡献——以第一人称引用形式呈现。

3. **关键缺失环节**：用一个短语指出从当前状态升级到可发表状态的关键瓶颈。格式：
   ```
   <font color="#c0392b"><b>　关键词。</b></font>
   ```

4. **"Before/After" 对比**：
   - Before → `<font color="#7f8c8d">"当前工作被理解成……"</font>`
   - After → `<font color="#27ae60"><b>"正确的贡献陈述应是……"</b></font>`

5. **结语**：`<font color="#c0392b"><b>这才是审稿人会认可的贡献。</b></font>`

### 模块 6：决策横幅（再次）

橙色大横幅，与 §1 使用相同措辞。

### 模块 7：复审要求

> <font color="#555555"><b>复审要求：</b>[具体列出需要补充的内容]</font>

### 模块 8：阅读范围脚注

```markdown
<p align="right"><font color="#95a5a6"><small>本审稿意见基于对 [列出所有已读文件] 的全文阅读。</small></font></p>
```

```

```

### 2. 金句引用（§5）


### 3. 关键缺失

```markdown

```

## 评估维度权重

在评估时，四个维度的权重如下：

1. **新颖性** — 最重要。决定工作的"发表价值天花板"。明确区分"方法原创性"、"应用新颖性"、"教学/工程贡献"、"复现/基础设施价值"四个层次。
2. **实验验证** — 次重要。决定工作是否"可被接收"。必须有基线对比（否则一票否决），强烈建议有真实数据/多案例。
3. **理论完备性** — 对控制/Audio 期刊重要。理论缺口不一定是发表阻碍（可在 Discussion/Limitations 中坦诚讨论），但应当识别并标注。
4. **表述与结构** — 影响审稿体验。文档碎片化、"未完成感"、缺少 Related Work 是最常见的问题。

---

## 决策逻辑

根据四个维度的评估结果，确定总评决策：

| 条件 | 决策 |
|:---|:---|
| 核心方法非原创 + 无基线对比 + 无硬件实验 | Not suitable as a research paper in current form → 建议重定位为教学/软件/开源 |
| 有 ≥1 个原创原子 + 缺基线对比/理论分析 | Major Revision |
| 有原创贡献 + 实验充分但局部缺失 | Minor Revision |
| 四个维度均充分覆盖 | Accept with minor edits |

## 使用示例

当用户输入类似以下触发词时，应用本技能：

- "帮我审一下 demoX 的发表可行性"
- "这个 demo 能发什么期刊？"
- "review publishability of demoX"
- "投稿前景评估"

**工作流程**：

1. **阅读阶段**：完整阅读目标目录下的所有 `.m` 脚本、`.md` 文档、`README.md`、核心函数
2. **分析阶段**：按四个维度提取信息——
   - 新颖性：区分每个技术要素的来源（已有文献 vs. 作者独立）
   - 理论完备性：识别理论缺口、未证明的声明
   - 实验验证：盘点已有实验 vs. 缺失实验（基线对比是红线）
   - 表述与结构：评估文档完整性、叙事逻辑
3. **定位阶段**：根据原创贡献的层次，判断最佳发表渠道（研究论文/教学论文/软件论文/开源）
4. **输出阶段**：严格按 8 模块结构输出审稿意见，直接写入目标目录下的 `Review_<demo>_Publishability.md`
